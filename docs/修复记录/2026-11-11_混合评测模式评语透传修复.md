# 2026-11-11 混合评测模式评语透传修复

## 问题

Langfuse「Judge 评分」节点与 judge.json 落盘中，六个主观维度的评分理由恒为空串，
「Judge 评审」GENERATION 节点缺失，judge.json 的 `_judge_model` 为空串。

- 现象定位：INT-001 真实跑（317s，八维分数全部落库）后 UI 上只有分数没有评语，
  仅忠实度一维有理由（该维走 `build_faithfulness_reason` 现场合成通道，不经评语链路）。
- 根因一（主体）：`evaluation_orchestrator.evaluate()` 用 `_extract_scores` 合并
  分数时只收数值键，Judge 返回的 `details`/`summary` 评语数组与 `_judge_usage`
  token 开销、adapter 的评分理由全部静默丢弃；而消费方（`report_trace`、
  `build_optimized_scores`）按纯 Judge 路径既有的 `_all_runs[0].details` 形态读理由，
  混合模式下该形态不存在 → 恒为空串。
- 根因二（首轮修复后的真实链路半截失效）：首轮实现按 `_run_evaluation` 中间层
  包装形态收 `reasons` 键，但真实 `evaluate_quality` 最终形态把理由放在下划线键
  `_reasons`——差一个键名，DeepEval 路由维（相关性/完整性/忠实度/数据准确性）
  评语仍空。离线契约用例只覆盖了中间层形态，未覆盖最终形态，故离线全绿而真实半截失效。

## 修复

- `core/evaluators/evaluation_orchestrator.py`：`evaluate()` 保留 judge 原始返回
  与 adapter 理由；合并后按消费方既有 `_all_runs` 形态补齐透传——评语按分数
  来源对齐（Judge 打分的维用 Judge 评语，DeepEval 覆盖分数的维用 adapter 已
  中文化评语，防止评语与分数错位）；同时透传 `_judge_usage`（恢复「Judge 评审」
  GENERATION 节点）与 `_judge_model`；理由收集兼容 `reasons` 与 `_reasons` 两种形态。
  消费方（report_trace / build_optimized_scores / score_sink）零改动。
- `test_cases/eval_contract/test_deepeval_routing_offline.py`：新增
  `TestReasonPassthrough` 5 条契约用例——包装形态来源对齐、真实 adapter 扁平
  `_reasons` 形态、纯 Judge 路径 details 保留、无评语不伪造 `_all_runs`、
  `_all_runs` 不漏入 junit dimensions 属性。

## 验证

- 离线：eval_contract 15 passed；全量 `-m offline` 169 passed / 9 deselected / 2.23s
  （基线 164 + 新增 5，无损）。
- 真实（INT-001 两轮复跑）：首轮复跑 Judge 路由维评语出现、DeepEval 路由维仍空
  （暴露根因二）、「Judge 评审」GENERATION 节点与 token 数（5996→1701）恢复、
  judge_model 不再为空；`_reasons` 形态修正后二轮复跑全部维度评语齐备（用户确认）。
- 已知残留：「裁判评语」summary 字段依赖裁判模型按 prompt 输出，模型偶发省略时
  显示"无"（非必填字段的既有降级，非链路问题）。

## 遗留

- Score/Event 双通道对 dict 形态分数取数不对称（Score 解包 `.get("score")`、
  Event 直塞原值），当前 judge_result 扁平标量下一致，未对齐。
- 忠实度"0/0 条声明被原文支持"仍给满分 5.0 的宽松兜底语义未深查。
- robust 5 条真实用例缺 agent 标记的口径问题（前批遗留）。
